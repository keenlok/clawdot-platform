# SBot scoped self-extension and self-improvement design

Date: 2026-10-31. Planning base: `afa88c4ed3ee44be7c47dfa4b995db2d63601de3`.
Working checkout: `/path/to/worktrees/self-extension/sb_bot`.

## Outcome and boundaries

SBot should build a missing tool, test its candidate in an enforced sandbox, show a reviewable immutable revision, let a current group administrator activate it for that group, execute it in the sandbox, and support monitoring and revocation. Group administrators manage their group's tools inside operator-set capability ceilings. Routine tool approval does not require the global operator. DMs are separate private scopes: membership of a group never copies its tools, requests, results, credentials, or grants into a DM.

The recommended first release is a **complete, opt-in, local/test-chat implementation for pure JSON transformations**. Examples include unit conversion, deterministic text formatting, and splitting a supplied bill. It includes generation through the existing Provider, a real separate Docker worker, human review, chat activation, invocation and revocation. It cannot fetch websites, read chat history independently, write external systems, use credentials, install packages, modify its framework, or deploy itself. A generic `run_extension` dispatcher makes approved tools usable without importing generated Python into the bot or dynamically changing the core registry.

This is a bounded self-extension feature, not merely database scaffolding. Production deployment remains separate and unauthorized by this plan. General capability brokers, shared publication, generated-tool upgrades, and shared-framework proposals follow in the roadmap below. Existing reviewed read-only builtins keep their normal execution paths; generated code remains sandboxed even when it claims to be read-only.

## Grounding in the current repository

- `chatcore.plugin.BasePlugin` supports tools, commands, pending handlers, startup and privacy hooks; `BotApp` registers tools once. There is no dynamic loader.
- `ToolRegistry.call` checks top-level unknown/missing arguments, but does not fully validate JSON Schema types. The extension boundary must independently validate nested input and size limits.
- `ToolContext.is_admin` and `CommandContext.is_admin` are global operator authority. They must not be repurposed for group authority.
- `ConfirmService` binds actions to the requester and chat, claims them once, and expires them. It does not itself re-check current administrator status: extension commit handlers must do so.
- `ChatPlatform` has `is_member` but no group-admin method. Telegram already uses `get_chat_member`; add an optional adapter method without changing core contracts. An injectable callback keeps this compatible with the in-flight group-admin-permissions work.
- `build_app` explicitly constructs plugins and providers; Postgres is available for Telegram, memory repositories are normal for tests. `PrivacyPlugin` receives the plugin list.
- Production compose is non-root/read-only and has no Docker socket. Preserve it. The existing deployment archives `HEAD` and builds remotely; it is not an autonomous sandbox or safe dynamic-code loader.
- Local verification found a running Linux Docker daemon in Colima, seccomp/AppArmor advertised, and a Python 3.12 image present. No `runsc` binary was found. Ordinary containers share the guest kernel and are not a microVM or a proof against kernel exploitation. Restrict this implementation to explicitly enabled local/test operation pending a dedicated production sandbox review.

## Approaches and recommendation

| Approach | Usable result | Tradeoff |
|---|---|---|
| CLI laboratory first | Generate/test/review/run locally | Smallest security surface, but leaves the actual chat/group-admin goal unfinished. Keep only as a verification entry point. |
| **Bounded chat feature plus separate local worker** | Full request-to-revoke flow for pure transforms | Recommended. Real isolation and group boundaries, fixed capability ceiling, no generic broker or arbitrary dependencies. |
| General remote capability platform immediately | Network, stateful tools, credentials, upgrades | Much wider policy, infrastructure and integration scope; postpone until the narrow lifecycle has evidence. |

## Architecture and trust boundaries

`human -> fixed plugin handlers -> scoped repository + trusted generator -> authenticated worker client -> separate worker -> ephemeral container`

The trusted controller is a new `chatcore-extensions` plugin. It alone sees bot stores, the provider key and chat identity. The generator makes one bounded provider call with only the user's explicit specification and examples; no conversation history, credentials, database handles or tools. The response is strict JSON containing source, short description, and example cases. Generated Python has one `run(arguments)` entry point and uses the image's standard library. No dependency downloads, user Dockerfiles, launch arguments, filesystem paths or requested privileges are accepted.

The worker is a separate CLI process, not a plugin running Docker in production. A private Unix domain socket (parent directory 0700, socket 0600) plus a random bearer token read from a 0600 file authenticates the controller. Only fixed `/health` and `/run` endpoints exist. `/run` accepts a versioned bounded JSON envelope with trusted scope, revision digest, run ID, source and JSON arguments. The worker verifies the digest and applies its own fixed limits; callers cannot weaken policy. It has no provider key, production DB connection, Telegram token or deployment credentials. Launch it from a clean environment. It may access the local Docker daemon; neither the controller's production container nor any generated container receives the Docker socket.

For v1 every job is ephemeral, has no host mounts, no networking, and receives source/input over stdin. A trusted Python harness is passed as a fixed entrypoint and executes the source only inside the container. Full source and inputs never become shell arguments. Start by immutable local image ID, with no implicit pulls. Apply non-root UID/GID, read-only root, bounded tmpfs, all capabilities dropped, no-new-privileges, default seccomp, private PID namespace, memory/swap/CPU/PID limits, bounded stdin/stdout/stderr and a host-enforced deadline. Create/start/inspect/remove by exact randomly generated container name; never clean unrelated containers. Timeouts, cancellation, malformed output and stream overflow remove the container in `finally`. Docker flag details are in the [Docker run reference](https://docs.docker.com/reference/cli/docker/container/run); daemon privilege limitations are described in [Docker Engine security](https://docs.docker.com/engine/security/).

The private socket is intentionally a same-local-account transport. A production bot running as UID 10001 cannot simply traverse the worker's 0700 directory; production needs a separately reviewed transport/identity design, not relaxed socket permissions.

V1 constants: source <=32 KiB; specification <=4 KiB; request/result JSON <=16 KiB each; at most 8 test cases; each job <=5 seconds; 128 MiB memory and equal swap limit; 0.5 CPU; 32 PIDs; 16 MiB `/tmp`; 32 KiB combined captured streams; worker concurrency 2 with immediate busy response; generation <=60 seconds and <=4096 output tokens. Fixed ceilings are owned by reviewed code, not generated manifests. Run records retain status/duration/digest, not payloads or raw stderr. At most 100 invocations per scope/day and 5 builds per scope/day, counted atomically. A service-wide kill switch disables all extension dispatch. Three consecutive runtime failures suspend that scope's activation; a fresh admin confirmation is required to reactivate.

## Scope, authority and lifecycle

Use required `ChatRef` on every controller repository operation, including lookups by opaque ID or digest. Scope is always `ctx.chat`; no model-supplied target group, user, role, grant or credential fields. For a DM, require `ctx.chat.key == ctx.user.ref.key` before management, and never resolve it to a member group. For a group, management requires a fresh `is_group_admin(chat,user)` result. Errors, missing adapter capability and unknown roles deny. Allowed statuses are Telegram `creator` and `administrator`; `member`, restricted and departed users deny. Existing global-admin flags do not bypass this rule. The bot's allowlist/membership gate still applies before handlers. For direct unit-level handler invocation, inject an allowlisted-scope predicate as defense in depth.

Any admitted user can propose a tool with `request_extension(description, examples)`; it returns a pending action and persists only after requester confirmation. A current group admin can then `/extensions build <request-id>`; confirmation commits a bounded generation/test attempt. DM owners perform both steps privately. Generated cases are suggestions, not evidence of semantic safety; admin-supplied examples and fixed adversarial sandbox probes remain independent. Revision source and its complete manifest are immutable. Digest is SHA-256 over canonical versioned JSON containing source, description and cases. Test evidence binds that digest, sandbox policy version, harness digest and immutable runtime image ID. Re-running with changed policy creates new evidence; approval never follows a mutable name.

`/extensions review <revision-id> [page]` shows description, full digest, limits, test result and paginated source in the current scope. Review output is treated as untrusted text and never sent as privileged instructions to the model. `/extensions activate <revision-id> <full-digest>` presents a requester-bound confirmation with exact scope/digest/capability ceiling and evidence. On commit, re-check current role, scope, digest, passing evidence, policy/image identity and expiry. Record reviewer and activation atomically. This explicit approval is the review gate; a model cannot certify itself. Reject partial hashes and hidden “latest” aliases.

`list_extensions()` lists only current-scope approved names/descriptions/IDs. `run_extension(revision_id, arguments)` checks current activation and ceiling, executes the exact approved artifact via the worker and returns `ToolResult(untrusted=True)` (including errors). It never forwards stores, credentials or other chat data. A second activation/version check after worker completion suppresses outputs if revoked during execution. A short-lived in-flight job may finish after revocation (maximum five seconds); it has no external effects or persistent storage. Revocation denies all new starts immediately. That is the v1 cancellation contract, not a claim to instantly terminate every running process.

`/extensions revoke <revision-id>` is an immediate restrictive operation after a fresh role check; no confirmation delay. `/extensions status [revision-id]` exposes only scoped metadata: active/suspended/revoked, test status, counts, failures and timestamps. `/extensions activate` can reactivate a suspended/revoked tested revision only through fresh confirmation. A different source always needs a new immutable revision and review.

Use Postgres repository in real chat operation and a locked in-memory repository for tests/console. No automatic ephemeral fallback when Telegram persistence fails. Data tables: requests, immutable revisions, test evidence, per-scope activations with monotonically increasing epoch, and metadata-only audit/run records. Store source in the scoped repository initially; global deduplication/publication is postponed. Purging a chat deletes all its extension state. Purging a user removes their requests/revisions/reviews and revokes affected activations before deleting; never leave approval without its reviewer. Retention removes expired proposals/unactivated revisions and old run metadata; active artifacts remain until revoked/purged. Results are returned to the invoking chat and existing bot message retention applies.

## Roadmap and added self-improvement scope

Artifact SHA-256 revisions are not Git commits. V1 stores immutable scoped artifact revisions and review evidence; it does not claim to commit generated tools into Git. A later explicit export step can write a reviewed revision into a dedicated artifact repository with hooks disabled and no bot checkout access, then record both Git commit SHA and artifact digest. Source-framework changes already require the separate exact-Git-SHA handoff below.

1. **Execute now: pure-transform self-extension.** See the two implementation plans. Both stages together are the promised feature; stage A alone is a tested worker, not completion. No production changes.
2. **Generated-tool improvements.** A user/admin requests a new revision; compare against retained independent regression cases; generate and sandbox-test; show source/behavior diff; require fresh scoped activation; retain rollback reference; never auto-upgrade other groups. Add bounded group configuration proposals under the same live authority/confirmation policy. This reuses most of v1 but adds version comparison, regression ownership and rollback semantics.
3. **Capability broker and sharing.** Separately review typed read operations first, then external writes. Broker holds credentials, derives group grants itself, constrains service/route/method/request shape, rechecks scope and activation on every call, and applies network/SSRF controls and quotas. Generated code never receives raw secrets or general HTTP access. Writes require requester-bound confirmation of an exact broker operation; “read-only” labels do not bypass sandboxing. Global publication needs explicit publication review and proof that source/manifests/examples contain no private data; code reuse never copies activation, data or grants.
4. **Shared-framework proposals only.** SBot may propose patches in an isolated build environment and produce a tested exact-SHA review bundle. Human review/merge/release remains separate. No autonomous modification of shared runtime, deployment, sandbox policy, authentication or security ceilings is authorized. This is qualitatively more scope than improving generated tools, because it changes the trusted computing base.

## Acceptance and release gates

- **SE-01:** An ordinary group member can create a confirmed request; current group admin builds, inspects and activates; ordinary member invokes successfully; revoke prevents invocation. Demonstrate through `BotApp.handle`, then an opt-in local console/worker smoke flow.
- **SE-02:** Another group and a DM cannot list/read/build/activate/run/revoke artifacts using known foreign IDs, hashes or fabricated pending payloads. A DM owner can complete the private flow without publishing.
- **SE-03:** Fresh role checks at management and confirmation reject demotion, lookup failure and missing capability. Global `is_admin` retains its old meaning. No model-supplied scope/role can override identity.
- **SE-04:** Source, manifest, tests, runtime image and policy are digest-bound. Tampering, changed digest, failed/missing evidence, stale pending actions and duplicate confirmations cannot activate a revision.
- **SE-05:** Real container tests exercise and verify denial of attempts to read host sentinels or socket/keys, escape writable storage through paths/symlinks, connect over IPv4/IPv6/DNS, persist across jobs, exceed memory/PID/time/output ceilings, or execute source in the host process. No mocked runner can satisfy this gate. These are empirical boundary checks, not proof against arbitrary kernel/runtime exploits.
- **SE-06:** Worker auth, request bounds, fixed image/entrypoint policy and concurrency limits reject malicious callers; exceptions/timeouts/cancellation leave no task containers. Worker unavailable never falls back to host execution.
- **SE-07:** Revocation/suspension/kill switch block starts and suppress in-flight results; audit contains IDs/status only; quotas and privacy hooks work after restart and across concurrent requests.
- **SE-08:** Feature is off by default, existing tool behavior and 517-test baseline remain compatible; production compose/deploy scripts are unchanged. End-to-end tests include a real worker, not only fake generator/runner.
- **SE-09:** Handoff names exact full source commit SHA, base SHA, diff, test commands/results, sandbox image ID/digest, policy/harness digests and outstanding limitations. Never archive moving `HEAD` implicitly. Deploying that reviewed commit is a separate operator decision.

## Material decisions and blockers

No unavoidable blocker to local implementation was found. Docker is available and the existing Python image can be resolved to a full immutable image ID without a pull. Do not install VM runtimes or modify host policy. The group-admin integration is additive and must be reconciled with the parallel permissions change at final review; it is not a reason to broaden global admin privileges. Real Telegram testing depends on a separately authorized test group and bot membership; fake-adapter plus real-worker tests can complete without touching production. Production readiness is blocked on a dedicated sandbox host/runtime decision, controller-to-worker transport/deployment design, and explicit release authorization. These do not justify silently presenting local tests as production readiness.
